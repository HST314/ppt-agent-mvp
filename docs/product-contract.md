# PPT Agent MVP 产品需求与流程契约

> 文档状态：需求基线（待用户整体审阅）  
> 适用范围：PPT Agent MVP  
> 文档目标：固化已确认的产品边界、用户流程、阶段门禁、运行模式、产物与主 Agent 对接约定；不规定具体技术框架、数据库、接口实现或 HTML 制作方法。

## 0. 2026-08 流程基线

本节覆盖本文后续章节中的旧流程表述；细化验收见 [`../业务场景需求.md`](../业务场景需求.md)。

- 用户确认样品后，系统自动创建全稿生成 Job 并进入全稿页；全稿页不再提供修改表单。
- 用户可在全稿页直接确定终稿，也可进入“自检与修改”执行检查、Prompt 修改、版本操作和问题处置。
- 检查是可选质量工具，不是交付门禁。终稿事实绑定精确 `deck_hash`，同时记录 `unchecked`、`stale`、`passed`、`issues_disposed` 或 `issues_remaining`。
- 交付拆分为“确定终稿”和“将离线包写入工程文件夹”两个动作；只有后者的持久化 Job 原子发布并校验成功后，任务才完成。
- 展示性图片允许 HTTP(S)、受限 Base64 和当前任务冻结资源的安全相对路径；交付时必须本地化远程/相对图片，离线包不得保留外部运行时依赖。

## 1. 产品定位

PPT Agent 是一个面向客户展示讲解场景的专业制作 Agent。它根据 Markdown 或 JSON 任务卡以及当前任务资源目录中的素材，依次完成整稿叙事结构、逐页大纲、HTML 样品页、完整 HTML 演示稿、质量检查、人工审核和交付。

MVP 先以可独立使用的 PPT Agent 工作区交付，形态参考现有 Image Agent。未来再接入由主 Agent 负责的统一任务编排系统。产品契约须为后续任务卡调度与结果回传保留边界，但本期不要求实现统一主 Agent 入口。

在完整系统中：

- 主 Agent 负责理解客户多模态资料、整理任务卡、管理任务级依赖、启动/暂停/取消专业 Agent 并接收结果；
- PPT Agent 不读取客户原始资料，不重新裁决客户资料，只处理主 Agent 已整理好的任务卡与获授权资源；
- 一项主任务只对应一个 PPT、一个 PPT Agent 工作区，不要求在同一主任务内并行实例化多个 PPT Agent；
- Image Agent 的多任务实例可并行生成图片。全部所需前置图片资源完成后，主 Agent 才启动 PPT Agent；
- PPT Agent 与技术方案 Agent、报价 Agent 可在各自前置资源就绪后并行运行。

## 2. MVP 范围

### 2.1 MVP 必须支持

- 用户在 PPT Agent 工作区直接创建任务；
- 接收 Markdown 或 JSON 格式任务卡；
- 自动扫描当前任务获授权的公共资源目录；
- 大纲生成前的可配置澄清问答；
- 生成并编辑整稿叙事结构 Markdown；
- 生成并编辑逐页大纲 Markdown；
- 生成、预览和反复调整 HTML 样品页；
- 基于确认样品生成完整 HTML 演示稿；
- 通过 Prompt 修改整稿、指定页面或指定元素；
- 版本保存、对比与非破坏回退；
- 独立模型基于 HTML 和最初大纲进行质量检查；
- manual / quick / auto 三种运行模式；
- 可选自检、问题处置、终稿冻结及明确离线交付；
- 交付完整 HTML、资源、Markdown 产物和结果摘要；
- 桌面端友好的完整编辑体验。

### 2.2 MVP 不要求

- PDF 或 PPTX 导出；
- 移动端适配；
- PPT Agent 直接解析客户原始 PDF、Office、音频或视频资料；
- 生成模型或检查模型查看图片、页面截图；
- 为图片简介、索引等信息定义主 Agent 必填字段；
- 预览缩略图；
- 统一主 Agent、任务看板和审批收件箱的完整实现；
- 在同一主任务下并行创建多个 PPT Agent 实例；
- 在本契约中规定 HTML 具体制作技术。HTML 制作与设计细则由专门 Skill 指导。

## 3. 角色与职责边界

### 3.1 用户

- 创建独立 PPT 任务并提供任务卡；
- 回答大纲前的必要问题；
- 查看、直接编辑或通过 Prompt 修改叙事结构和逐页大纲；
- 审核并确认样品页；
- 预览和修改完整演示稿；
- 处理检查问题，选择修复、已手工处理、接受/豁免或暂不处理；
- 最终点击“确定终稿”，并在交付页明确写入离线包。

### 3.2 主 Agent（未来接入）

- 读取并理解客户原始多模态资料；
- 生成经过把关的详细任务卡；
- 等待本次 PPT 所需的全部前置图片资源完成；
- 冻结并下发任务输入和资源集合；
- 管理 PPT 任务级依赖、启动、暂停、取消与结果接收；
- 不介入 PPT Agent 内部的大纲、HTML、检查和版本状态。

### 3.3 PPT Agent

- 校验任务输入并组织必要澄清；
- 扫描资源目录，通过图片配套 Markdown 获取素材含义与引用信息；
- 管理叙事结构、逐页大纲、样品、全稿、检查和版本；
- 按阶段加载系统内部选定的 Skill；
- 执行生成与修改，并保持未指定范围不变；
- 将检查与生成分离，不以生成阶段的自述替代独立审核；
- 只有用户确定终稿且离线包成功写入、校验后才报告完成。

### 3.4 检查模型

- 作为不继承生成上下文的独立模型运行；
- 只接收最初大纲与待审 HTML；
- 不接收生成对话、生成模型自述或中间推理；
- 不看图片及页面截图，仅通过 HTML 推断潜在渲染与质量问题；
- 输出结构化问题、严重度、影响范围和修改建议，不自行决定最终交付。

## 4. 输入与资源契约

### 4.1 显式输入

PPT Agent 的显式输入仅为 Markdown 或 JSON 任务卡。最小业务信息为：

- 演示目标；
- 受众；
- 核心主题。

页数、语言、画布比例、风格等可以在任务卡中提供。未提供时可采用可见的默认值或 Agent 建议值，并在大纲确认前向用户展示和允许修改。

若任务卡明确提出强页数要求，叙事结构和逐页大纲必须遵守；未提出时，页数由逐页大纲自然决定。完整 HTML 的页数必须与最终确认的逐页大纲一致。

### 4.2 资源目录

- PPT Agent 自动扫描当前任务获授权的公共资源目录；“公共”仅表示当前主任务内可共享，不代表跨客户或跨项目全局可见；
- 默认每张图片都有一份对应的 Markdown 描述；
- 任务卡可选填图片简介、索引等信息，但不得强制主 Agent逐项填写；
- 模型通过文件索引、Markdown 描述及任务语义使用资源，不以看图理解为前提；
- 前置图片不是独立创建任务的启动硬条件，没有图片时也可形成内容规划或待补资源位。

### 4.3 输入校验与缺失处理

- 只阻断影响演示目标、受众、事实正确性或关键交付约束的缺失项；
- 阻断项进入等待补充；
- 非阻断项采用明确默认值或显式假设继续，并在大纲确认前集中展示；
- PPT Agent 不读取客户原始资料，因此不存在由 PPT Agent 在原始资料和主 Agent 摘要之间裁决的流程。

### 4.4 输入冻结

未来由主 Agent 启动时，启动即冻结本次输入与资源集合。主 Agent 应在全部所需前置图片资源就绪后启动任务。

运行中新增或更新的上游资源不进入当前任务，不静默替换素材，也不触发自动重生成。若需采用新资源，应由上游重新组织任务输入。MVP 独立工作区中，资料仅允许在大纲确认前新增或替换。

## 5. Skill 使用契约

- Skill 由系统内部决定，不要求用户选择或感知；
- 任务运行时按阶段渐进式披露，避免一次性注入全部规则；
- 叙事结构、大纲、HTML 生成、局部修改和检查分别加载当前动作所需规则；
- 具体页面字段、版式、资源组织、检查规则和 HTML 制作方法由 Skill 定义，本产品契约不重复硬编码。

## 6. 运行模式

MVP 保留 `manual`、`quick` 与兼容既有任务的 `auto` 三种模式，不单列 `solo`。

### 6.1 manual

- 关键生成动作和阶段推进由人工触发；
- 必要人工门禁始终保留；
- 样品确认后自动启动全稿生成；
- 独立检查由用户按需触发，结果提交人工处置。

### 6.2 auto

- 非审批动作在前置条件满足后自动推进；
- 全稿检查后可在配置的最大轮数内自动修复并复检；
- 原先讨论的 solo 自动修复闭环能力并入 auto；
- 样品确认、终稿确认和最终写包仍必须由人工完成；
- 达到修复轮数上限或遇到阻断时停止自动推进并请求人工介入。

### 6.3 quick

- 创建任务时必须明确 1–200 页的最终页数，并写入冻结任务卡约束；
- 澄清最多一轮，只保留阻断问题，非阻断缺失采用可见默认值或假设；
- 自动保存叙事结构与逐页大纲并推进到样品确认，不跳过中间产物；
- 样品确认、终稿确认和最终写包仍必须由人工完成。

### 6.4 模式切换

- 任务执行中允许切换模式；
- 只影响切换后的待执行动作；
- 不撤销已完成动作，也不改写既有版本。

## 7. 端到端流程

### 阶段 0：任务创建与资源扫描

1. 用户创建任务并提交 Markdown/JSON 任务卡；
2. Agent 校验最小业务信息；
3. Agent 扫描当前任务资源目录及图片配套 Markdown；
4. 系统展示约束、默认值、显式假设、资源摘要与缺失项。

输出：任务输入快照、资源清单、缺失项与假设清单。

### 阶段 1：大纲前澄清

1. Agent 仅提出会影响路径、事实或关键交付结果的问题；
2. 问题采用选择题形式，并提供 `Other`；
3. 选择 `Other` 时，用户可输入或上传 Prompt 作为回答；
4. 问题、选项、回答和关键假设在工作区可见；
5. 用户在确认前可修改回答并重新生成后续产物。

MVP 由人工回答；未来可由主 Agent 根据已读取的客户资料回答。

输出：确认后的问答与假设集。

### 阶段 2：整稿叙事结构

1. Agent 先生成独立的整稿叙事结构 Markdown；
2. 产物至少表达核心结论、叙事路径和章节组织；
3. 用户可查看、直接编辑、通过 Prompt 修改、局部/整体重生成、增删或调序；
4. 用户直接编辑后即形成新的权威版本，Agent 只做格式与引用检查，不静默改写内容。

输出：版本化的整稿叙事结构 Markdown。

### 阶段 3：逐页大纲

1. Agent 基于已确认叙事结构生成逐页大纲 Markdown；
2. 逐页大纲是 HTML 生成的权威内容输入，最低字段由 Skill 定义；
3. 图片在大纲中使用 Markdown 图片引用，文本预览可显示资源；
4. 原则上一张图片不跨页复用，通常一图一页，允许少量一页多图，细则由 Skill 指导；
5. 用户可直接编辑、Prompt 修改、指定页/章节重生成、整体重生成、增删或调序；
6. 局部操作默认只改变指定范围。若会影响其他页面，先说明影响范围；
7. 用户直接编辑即形成权威新版本，Agent 仅检查格式和引用；
8. 大纲阶段不生成视觉预览。

门禁：

- manual 模式下，用户必须明确确认大纲后才能进入样品页阶段；
- auto 模式可自动完成叙事结构到逐页大纲的非审批推进；
- 已确认大纲仍可返回修改，但必须形成新版本，并标记现有 HTML 可能受影响的范围。

输出：版本化的逐页大纲 Markdown。

### 阶段 4：HTML 样品页

1. Agent 推荐最能代表视觉风格和主要版式的页面，用户可在生成前改选；
2. 默认生成 2 页，可在 1 页至整稿全部页之间调整；
3. 使用已确认大纲和真实资源生成可播放的完整 HTML 页面，不使用线框、占位文本或占位图；
4. 前端预览区渲染样品页；
5. 用户可针对页面、元素或全局视觉方向提交 Prompt；
6. Prompt 作用范围由 Agent 结合语义和当前选择自行判断，不要求用户每次额外选择；
7. 样品页不执行自动检查，由人工直接预览并反复调整；
8. 用户必须明确确认样品；确认成功后系统自动创建全稿生成 Job 并进入全稿页，auto 模式也不得绕过确认。

输出：确认样品页、全局视觉方向、可复用版式规则和全局 Prompt 约束。样品页局部特例不得自动泛化为全稿规则。

### 阶段 5：完整 HTML 演示稿

1. 确认样品后，一次生成逐页大纲规定的全部剩余页面；
2. 已确认样品页直接纳入全稿并尽量保持不变；
3. 若全局一致性确需调整样品页，先提示影响；
4. 完整演示稿在预览区按固定画布比例播放与讲解；
5. 用户可直接将当前候选确定为终稿，或进入“自检与修改”；
6. 全稿页只提供浏览与下一步决策，修改整稿、指定页或指定元素集中在“自检与修改”；
7. 涉及内容或叙事的修改先形成新的大纲版本，再更新受影响 HTML；纯视觉修改不改大纲。

输出：候选完整 HTML 演示稿及其与大纲版本的对应关系。

### 阶段 6：自检与修改（可选）

1. 全稿生成后不强制自动检查，用户可直接确定终稿或按需执行检查；
2. 后续修改优先检查受影响范围，并补充必要的整稿一致性检查；
3. 检查覆盖元素级、页面级和整稿级，具体规则由 Skill 提供；
4. 检查模型只依据最初大纲和待审 HTML，不继承生成上下文，不看图片或截图；
5. manual 模式只展示问题与建议，由人工决定后续动作；未检查或仍有遗留问题不阻断终稿确认；
6. auto 模式按配置的最大轮数自动修复并复检；
7. 每轮检查和修复结果在工作区可见；
8. 达到上限仍有问题时停止循环，列出遗留问题、影响页面和建议动作，进入人工审核，不得虚假标记完成。

输出：检查报告、修复记录、遗留问题和建议动作。

### 阶段 7：终稿确认

1. 用户在完整预览中逐页查看，无需逐页打勾；
2. 用户可针对问题直接提交 Prompt；
3. 每个问题支持“让 Agent 修复”“我已手工处理”“接受/豁免”“暂不处理”；
4. 支持对同类问题批量执行相同动作；
5. 用户可在未检查、报告过期或仍有遗留问题时确定终稿，系统必须记录该状态与问题计数；
6. 所有处理和豁免均保留记录；
7. 终稿事实绑定当前候选的精确 hash，后续候选变化会使其失效。

输出：审核处置记录、未解决/已豁免问题及可交付候选版本。

### 阶段 8：离线写包与交付

只有用户已确定终稿，并明确点击“将离线包写入工程文件夹”，且原子发布与离线校验成功后，任务才算完成。生成全稿、确定终稿或检查通过均不等同于完成。

交付后允许基于已交付版本继续修改：

- 原交付版本保持不变且可回退；
- 新修改形成候选版本；
- 新候选版本必须重新由用户确定终稿后才能再次交付；检查仍为可选质量步骤。

## 8. 修改契约

- Agent 结合当前阶段、当前选中页/元素和 Prompt 语义识别修改对象；
- 界面显示 Agent 理解的修改目标；
- 仅当不同理解会明显改变结果或影响范围时追问；
- 其他情况直接执行，完成后展示修改摘要和对比，不设置执行前确认；
- 一次 Prompt 可统一修改多页或多个元素，只重生成受影响范围；
- 未指定范围默认保持不变；
- 人工明确意图优先于自动修复，若与质量规则冲突则由用户决定；
- 人工修改不设固定轮数；自动检查/修复受配置的最大轮数限制。

## 9. 版本与回退契约

- 每次直接编辑、Prompt 修改、自动修复及阶段确认均形成可回退版本；
- 叙事结构、逐页大纲和 HTML 分别保留版本，并记录对应关系；
- 预览默认切换到新版本，同时显示修改摘要；用户可按需比较前后版本；
- 回退为非破坏操作：将历史版本复制为新的当前版本，不删除后续历史；
- 回退大纲后，如现有 HTML 与当前大纲不一致，必须明确标记；由用户选择重新生成受影响范围，不得静默覆盖；
- 时间线应展示版本来源、修改摘要、操作者及大纲/HTML 对应关系。

## 10. 状态与生命周期契约

### 10.1 业务阶段

规范业务阶段至少包括：

1. 任务/资料；
2. 澄清；
3. 叙事结构；
4. 逐页大纲；
5. 样品；
6. 全稿；
7. 检查；
8. 人工审核；
9. 已交付。

### 10.2 正交运行状态

运行状态不得替代业务阶段。需要人工介入时保留当前业务阶段，并附加：

- `waiting_for_user`；
- 等待原因；
- 所需动作；
- 直达入口。

人工等待不得笼统标记为失败。执行期间向用户展示当前阶段、正在执行的动作、进度和可理解的等待原因，不展示内部思维过程。

### 10.3 暂停、取消与中断

- 主 Agent 未来可暂停或取消 PPT 任务；
- 收到暂停/取消后停止启动新动作，并尽量让当前原子动作安全收尾；
- 保存最后成功版本并回报结果；
- 执行失败或中断时保留最后成功产物；
- 界面明确展示失败动作、影响范围以及重试、修改输入或人工处理选项；
- 不清空成果、不无限重试、不只暴露技术错误日志。

## 11. 工作区交互契约

MVP 只支持桌面端完整体验。

### 11.1 信息架构

单工作区固定提供以下阶段视图，并始终保留预览与对话入口：

- 任务/资料；
- 大纲（含叙事结构与逐页大纲）；
- 样品；
- 全稿；
- 检查；
- 版本。

用户进入工作区时，自动定位当前阶段和待处理事项，并展示最新产物预览与下一步主操作。

### 11.2 导航与编辑

- 已产生内容可自由查看；
- 尚未到达的阶段只展示前置条件，不允许绕过必要门禁；
- 大纲同时支持 Markdown 直接编辑与 Prompt 修改；
- HTML 预览支持选择页面和可识别元素，选中对象自动作为 Prompt 上下文，也允许用户用文字指定其他范围。

### 11.3 检查问题

- 按严重度和页面分组；
- 支持逐项处理及同类问题批量操作；
- 预览与问题列表联动定位对应页面；
- 未来非自动闭环场景下，问题同时形成工作区待处理项和统一系统审批收件箱事项，并可直达对应页面。

### 11.4 与统一主看板的边界（未来）

- PPT 工作区负责深度编辑；
- 主看板仅展示规范阶段、总体进度、当前动作、等待原因、待人工事项、最新产物摘要和错误摘要；
- 主看板提供进入 PPT 工作区的入口；
- 不向主看板同步内部推理或完整对话。

## 12. 检查与交付规则

### 12.1 检查范围

检查应覆盖：

- 元素级：潜在溢出、越界、遮挡、对比度及资源引用等；
- 页面级：层级、布局、信息密度、视觉一致性等；
- 整稿级：叙事连贯、风格、术语与数据一致性等。

具体判断规则由 Skill 提供。MVP 的检查结论来自对 HTML 和最初大纲的模型推断，不宣称完成截图级视觉验证。

### 12.2 严重度与交付

- 阻断级与普通警告均须显式显示并保留处置记录；
- 用户可以带遗留问题确定终稿，交付摘要必须记录问题数量、阻断数量和检查状态；
- 达到自动修复上限不能被视为检查通过；
- 检查通过也不能替代终稿确认与离线写包。

### 12.3 核心交付物

- 完整 HTML 演示稿；
- 演示所需资源；
- 最终整稿叙事结构 Markdown；
- 最终逐页大纲 Markdown；
- 资源清单；
- 版本/状态摘要；
- 便于主 Agent 使用的结果说明。

远程图片和相对图片必须在交付时本地化并通过 hash 校验；Base64 图片可在受限媒体类型和大小内保留内嵌。离线包不得依赖外部图片、脚本、字体或 CDN。

不要求预览缩略图、PDF 或 PPTX。

### 12.4 回传主任务（未来）

PPT Agent 向主 Agent 回传：

- 完成状态；
- 已确认交付版本；
- 产物路径或索引；
- 大纲与 HTML 版本对应关系；
- 检查摘要；
- 未解决问题与已豁免问题。

不回传内部完整日志、模型推理或完整对话。

## 13. 关键门禁

| 门禁 | manual | quick | auto | 是否可绕过 |
|---|---|---|---|---|
| 阻断输入补齐 | 人工补齐 | 人工补齐 | 人工补齐 | 否 |
| 大纲进入样品 | 用户确认 | 可自动推进 | 可自动推进 | manual 不可绕过 |
| 样品进入全稿 | 用户确认 | 用户确认 | 用户确认 | 否 |
| 检查后的修复 | 人工决定 | 限定轮数内自动闭环 | 限定轮数内自动闭环 | 达上限后不可继续自动 |
| 阻断问题处置 | 修复或明确豁免 | 修复或明确豁免 | 修复或明确豁免 | 否 |
| 最终完成/交付 | 用户确认 | 用户确认 | 用户确认 | 否 |

## 14. MVP 验收标准

以下场景全部成立，才视为 MVP 产品闭环完成：

1. 用户可用 Markdown 或 JSON 任务卡创建任务；
2. 系统可扫描任务资源目录，并在不要求模型看图的情况下使用图片配套 Markdown；
3. 缺少阻断信息时进入可理解的人工等待，非阻断缺失采用可见默认值或假设；
4. 用户可完成大纲前选择题问答，并使用 `Other` 提交自定义回答；
5. 系统先生成可编辑的叙事结构 Markdown，再生成可编辑的逐页大纲 Markdown；
6. 用户直接编辑或 Prompt 修改后形成新版本，局部修改不污染未指定范围；
7. 系统默认推荐并生成 2 个可调整数量的真实 HTML 样品页；
8. 样品页可在预览区反复人工调整，未经用户确认不得生成全稿；
9. 确认样品后生成与最终大纲页数一致的完整 HTML 演示稿；
10. 用户可修改整稿、指定页和指定元素，并查看摘要、对比和版本关系；
11. 完整 HTML 由独立模型仅依据最初大纲和 HTML 进行元素、页面、整稿三级检查；
12. manual 模式把修复建议交给人工，quick/auto 模式在最大轮数内自动修复并复检；
13. 达到上限仍有问题时停止并进入人工处理，不虚假完成；
14. 阻断问题未解决且未明确豁免时不能交付；
15. 只有用户明确点击“确认完成/交付”后才报告完成；
16. 交付物包含 HTML、资源、两类 Markdown、资源清单、版本/状态摘要和结果说明；
17. 已交付版本可继续派生新候选版本，原交付版本保持不变且可非破坏回退；
18. 桌面端可完整完成上述流程。

## 15. 后续阶段（不属于本契约的实现内容）

本契约整体确认后，再依次开展：

1. 基于本契约编写最终技术方案；
2. 定义任务卡、状态、产物、检查报告及回传结果的机器契约；
3. 形成开发任务列表、依赖关系与验收映射；
4. 对 PPT Agent MVP 仓库进行实现设计与迭代开发；
5. 后续接入主 Agent、统一任务看板和审批收件箱。
